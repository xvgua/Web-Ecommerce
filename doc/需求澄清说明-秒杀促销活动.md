## 二、需要澄清的核心问题

### Q1：秒杀活动的核心模型

秒杀活动应该包含哪些要素？以下是几种常见方案：

**方案 A — 简单秒杀（推荐起步）**

- 在现有商品上设置秒杀价 + 秒杀库存 + 秒杀时间段
- 不新建活动表，直接在 `product` 或 `product_sku` 表增加秒杀字段
- 优点：实现快、改动小
- 缺点：灵活性低，难以管理多场次

**方案 B — 独立活动表**

- 新建 `seckill_activity` 表（活动名称、开始/结束时间、状态）
- 新建 `seckill_product` 表（关联活动 + 商品/SKU + 秒杀价 + 秒杀库存）
- 优点：灵活，支持多场次、可复用商品
- 缺点：新增实体多，前后端改动大

**方案 C — 通用促销引擎**

- 抽象"促销规则"（秒杀是一种促销类型，还可扩展拼团、满减等）
- 优点：扩展性强
- 缺点：过度设计，不适合当前阶段

> **请选择：** 你倾向于哪种方案？或描述你心中的秒杀活动是什么样的？

### Q2：秒杀库存管理策略

秒杀的核心难点是**高并发库存扣减**。以下是几种策略：

**策略 A — 数据库行锁（简单可靠）**

- `UPDATE seckill_product SET stock = stock - 1 WHERE id = ? AND stock > 0`
- 优点：不依赖 Redis，数据一致性强
- 缺点：并发量受限于 MySQL，约 500–1000 QPS

**策略 B — Redis 预扣库存（高性能）**

- 活动开始前将库存加载到 Redis，扣减在 Redis 中完成，异步同步到 DB
- 优点：抗高并发（万级 QPS）
- 缺点：Redis 与 DB 数据一致性需额外处理

**策略 C — Redis + Lua 原子扣减（推荐）**

- 使用 Lua 脚本在 Redis 中原子性地校验 + 扣减库存
- 优点：原子操作，无竞态条件
- 缺点：需编写 Lua 脚本

> **请选择：** 你期望的并发量级是多少？是否需要 Redis 扛并发，还是数据库方案即可满足实验要求？

### Q3：秒杀与现有订单流程的关系

秒杀订单流程是否复用现有下单流程？

**选项 A — 完全复用现有流程**

- 秒杀商品加入购物车 → 走正常下单 → 支付
- 优点：零额外开发
- 缺点：无"秒杀感"，用户可能加购后不付款占用库存

**选项 B — 独立秒杀下单流程（推荐）**

- 秒杀商品**不走购物车**，直接"立即秒杀" → 进入秒杀确认页 → 快速支付
- 秒杀订单锁定时间（如 15 分钟内未支付自动释放库存）
- 优点：体验好，库存不会长时间占用
- 缺点：需新增秒杀下单接口 + 超时取消定时任务

**选项 C — 混合模式**

- 秒杀商品也可以加购物车（按秒杀价），结算时校验秒杀是否还生效

> **请选择：** 你希望秒杀走独立流程，还是复用购物车+下单流程？

## 三、建议的最小可行方案（MVP）

综合考虑实验要求（进阶功能 0.5 分）和实现成本，建议以下 MVP 范围：

### 后端

1. 新增 `SeckillActivity` 实体 + `SeckillProduct` 实体
2. 新增 `SeckillController`（客户端接口：活动列表、活动详情）
3. 新增 `AdminSeckillController`（管理后台 CRUD）
4. 复用现有订单流程，秒杀商品走独立秒杀下单接口
5. 使用 Redis + Lua 做库存预扣（体现 Redis 缓存优化的拓展能力）
6. 使用 `@Scheduled` 定时任务处理超时未支付订单的库存释放

### 前端 — 客户端

1. 首页秒杀楼层接入真实数据（替换硬编码占位）
2. 秒杀专场页 `/seckill`（活动列表 + 倒计时 + 秒杀商品展示）
3. 秒杀详情/确认页（秒杀价、倒计时、立即秒杀按钮）

### 前端 — 管理后台

1. 秒杀活动管理页（列表、新增、编辑、删除）
2. 秒杀活动表单（选择商品/SKU、设置秒杀价、秒杀库存、时间范围）

### 不纳入 MVP

- 防刷限流（复杂，实验环境不需要）
- 拼团/其他促销类型
- 秒杀通知/提醒
- 秒杀数据统计独立 Dashboard
