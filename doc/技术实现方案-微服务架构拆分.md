# 微服务架构拆分 — 技术实现方案

> 编写日期：2026-06-05
> 拆分范围：商品、订单、用户三大核心模块

---

## 一、现状分析

### 1.1 当前架构

```
┌──────────────────────────────────────────────────────┐
│                  ecommerce-backend                    │
│                  (单体 Spring Boot)                    │
│  controller/  controller/admin/  service/  mapper/   │
│  商品 + 订单 + 用户 + 购物车 + 收藏 + 秒杀 + 评价 ...  │
│                      ↓ 直连                           │
│              MySQL 8.0    Redis 7                     │
└──────────────────────────────────────────────────────┘
```

| 维度 | 当前状态 |
|------|---------|
| 代码组织 | 单项目按包分层（controller / service / mapper / entity） |
| 部署单元 | 1 个 backend 容器 |
| 数据库 | 单一 MySQL `ecommerce` 库，20+ 张表 |
| 服务通信 | 进程内方法调用 |
| 事务管理 | Spring `@Transactional` 本地事务 |
| 缓存 | Redis（验证码 + 热点数据缓存） |

### 1.2 当前问题

1. **耦合度高** — `OrderServiceImpl` 直接注入 `ProductMapper`、`CartMapper`、`UserMapper`，业务边界模糊
2. **部署粒度粗** — 改一行用户逻辑也要全量重新构建 + 部署整个 backend
3. **扩展受限** — 无法单独对订单模块扩容；秒杀期间商品查询和下单抢同一进程资源
4. **技术锁定** — 无法对不同模块选择更适合的技术（如搜索模块用 Elasticsearch 需改整个项目）

## 二、拆分目标

### 2.1 目标架构

```
┌─────────┐  ┌──────────┐  ┌──────────┐  ┌──────────────┐
│ Gateway │  │ 用户服务  │  │ 商品服务  │  │  订单服务     │
│ :8080   │  │  :8082   │  │  :8083   │  │   :8084      │
│ 统一入口 │  │ 注册/登录 │  │ CRUD/搜索 │  │ 下单/支付    │
│ 路由/鉴权│  │ 个人信息  │  │ 分类/轮播 │  │ 退款/导出    │
└────┬────┘  │ 地址管理  │  │ 收藏/秒杀 │  │ 购物车       │
     │       └────┬─────┘  └────┬─────┘  └────┬─────────┘
     │            │              │              │
     └────────────┴──────────────┴──────────────┘
                  │              │              │
            user_db        product_db      order_db
           (独立 schema)   (独立 schema)   (独立 schema)
                  │              │              │
                  └──────────────┴──────────────┘
                        共享 Redis 集群
```

### 2.2 拆分原则

| 原则 | 说明 |
|------|------|
| **按业务边界** | 每个服务对应一个完整的业务领域，拥有自己的数据 |
| **高内聚低耦合** | 服务内部高度自治，服务间仅通过 API 通信 |
| **独立数据源** | 每个服务拥有独立数据库 schema，不共享表 |
| **渐进式拆分** | 一次拆一个服务，每步验证全流程可用 |

## 三、服务边界定义

### 3.1 用户服务 (user-service)

| 项 | 内容 |
|----|------|
| **端口** | 8082 |
| **职责** | 注册、登录、个人信息、地址管理、意见反馈、客服消息、公告管理 |
| **数据库表** | `user`, `admin`, `address`, `feedback`, `conversation`, `chat_message`, `quick_reply`, `announcement` |
| **对外 API** | `POST /api/auth/register`, `POST /api/auth/login`, `GET/PUT /api/user/profile`, `GET/POST/PUT/DELETE /api/user/addresses`, `POST /api/feedback`, `GET/POST /api/conversations`, `GET /api/announcements` |
| **依赖** | Redis（验证码、Token 黑名单） |

### 3.2 商品服务 (product-service)

| 项 | 内容 |
|----|------|
| **端口** | 8083 |
| **职责** | 商品 CRUD、SKU 管理、分类管理、轮播图、收藏、秒杀活动、搜索、热词 |
| **数据库表** | `product`, `product_sku`, `category`, `banner`, `favorite`, `seckill_product`, `seckill_session`, `search_log`, `hot_keyword` |
| **对外 API** | `GET/POST /api/products`, `GET /api/products/{id}`, `GET /api/categories`, `GET /api/banners`, `POST/DELETE /api/favorites`, `GET /api/seckill` |
| **依赖** | Redis（热点缓存、秒杀库存预扣） |

### 3.3 订单服务 (order-service)

| 项 | 内容 |
|----|------|
| **端口** | 8084 |
| **职责** | 购物车、下单、支付、退款、评价、订单导出、优惠券使用 |
| **数据库表** | `cart`, `order`（含退款字段）, `order_item`, `payment_session`, `review`, `review_comment`, `review_like`, `coupon`, `user_coupon` |
| **对外 API** | `GET/POST/PUT/DELETE /api/cart`, `POST /api/orders`, `GET /api/orders/:id`, `PUT /api/orders/:id/pay`, `POST /api/orders/:id/refund`, `POST /api/reviews`, `GET /api/coupons`, `POST /api/user/coupons/*/receive` |
| **依赖** | 用户服务（获取用户地址信息）、商品服务（校验商品/扣库存）、Redis（支付会话） |

> **设计说明**：优惠券（`coupon`、`user_coupon`）归入订单服务而非用户服务，因为优惠券的核心动作（计算折扣、核销扣减）发生在下单流程中。用户领取优惠券通过订单服务的 Feign 接口完成。

### 3.4 服务依赖关系

```
user-service ←── 订单服务（下单时查用户地址；领取优惠券时校验用户）
                    │
product-service ←── 订单服务（下单时校验商品 + 扣库存）
```

> user-service 和 product-service 之间无直接依赖，彼此独立。
>
> **额外依赖**：用户创建/删除评价后，order-service 需通过 Feign 调用 product-service 更新 `product.avg_rating` 和 `product.review_count`（`ReviewFeignClient`）。这是 order → product 的次要写依赖，不影响核心下单链路。商品详情页的评价列表由前端分别调 `GET /api/products/{id}` 和 `GET /api/reviews?productId={id}` 组装，无需后端跨服务读取。

## 四、技术选型

### 4.1 核心技术栈

| 组件 | 选型 | 版本 | 说明 |
|------|------|------|------|
| 基础框架 | Spring Boot | 3.2.5 | 与当前版本保持一致 |
| 微服务框架 | Spring Cloud | 2023.0.x (Leyton) | 与 Spring Boot 3.2.x 兼容 |
| 服务注册/发现 | Nacos | 2.3.x | 阿里开源，同时支持配置中心 |
| 远程调用 | OpenFeign | 4.1.x | 声明式 HTTP 客户端，集成负载均衡 |
| 负载均衡 | Spring Cloud LoadBalancer | — | 替代已停维的 Ribbon |
| API 网关 | Spring Cloud Gateway | 4.1.x | 基于 WebFlux，性能优于 Zuul |
| 熔断降级 | Sentinel | 1.8.x | 阿里开源，比 Hystrix 更轻量 |
| 分布式事务 | Seata | 1.8.x | AT 模式，对业务侵入最小 |
| 链路追踪 | Micrometer Tracing | 1.2.x | Spring Boot 3.x 集成，配合 Zipkin 可视化 |

### 4.2 为什么不选其他方案

| 候选 | 不选择的原因 |
|------|-------------|
| Dubbo | 生态偏阿里，与 Spring Cloud 体系整合不如原生方案自然 |
| Eureka | 已停维，Spring Cloud 官方推荐 Nacos/Consul |
| Ribbon | Spring Cloud 已移除，用 LoadBalancer 替代 |
| Hystrix | 已停维，Sentinel 是主流替代 |
| Consul | Spring Cloud 官方也支持，但 Nacos 同时提供配置中心，功能更全 |

### 5.4 远程调用 (OpenFeign)

**商品服务暴露接口：**

```java
// product-service 的 controller 本身即可被 Feign 调用
@RestController
@RequestMapping("/api/products")
public class ProductController {

    @GetMapping("/{id}")
    public Result<ProductDTO> getProduct(@PathVariable Long id) {
        // ... 业务逻辑
    }

    @PutMapping("/{id}/stock/deduct")
    public Result<Void> deductStock(@PathVariable Long id,
                                     @RequestBody @Valid StockDeductDTO dto) {
        // ... 使用 UPDATE ... WHERE stock >= ? 乐观锁
    }
}
```

**订单服务定义 Feign 客户端：**

```java
// order-service/src/main/java/.../feign/ProductFeignClient.java
@FeignClient(name = "product-service")
public interface ProductFeignClient {

    @GetMapping("/api/products/{id}")
    Result<ProductDTO> getProduct(@PathVariable("id") Long id);

    @PutMapping("/api/products/{id}/stock/deduct")
    Result<Void> deductStock(@PathVariable("id") Long id,
                             @RequestBody StockDeductDTO dto);

    @GetMapping("/api/products/batch")
    Result<List<ProductDTO>> batchGetProducts(@RequestParam("ids") List<Long> ids);
}
```

**订单服务使用 Feign 调用：**

```java
@Service
@RequiredArgsConstructor
public class OrderServiceImpl implements OrderService {

    private final OrderMapper orderMapper;
    private final ProductFeignClient productFeignClient;  // 替代原来的 ProductMapper
    private final UserFeignClient userFeignClient;        // 替代原来的 UserMapper

    @Override
    // 注：此处仅为演示 Feign 调用模式，分布式事务方案见 5.6 节
    public OrderDTO createOrder(CreateOrderDTO dto) {
        Long userId = UserContext.getUserId();

        // 1. 远程获取用户地址
        Result<AddressDTO> addrResult = userFeignClient.getDefaultAddress(userId);
        if (!addrResult.isSuccess()) {
            throw new BusinessException("收货地址不存在");
        }

        // 2. 远程校验商品 + 扣库存
        for (OrderItemDTO item : dto.getItems()) {
            Result<ProductDTO> prodResult = productFeignClient.getProduct(item.getProductId());
            if (!prodResult.isSuccess() || prodResult.getData() == null) {
                throw new BusinessException("商品 " + item.getProductId() + " 不存在或已下架");
            }
            StockDeductDTO stockDTO = new StockDeductDTO(item.getQuantity());
            Result<Void> stockResult = productFeignClient.deductStock(
                item.getProductId(), stockDTO);
            if (!stockResult.isSuccess()) {
                throw new BusinessException("商品库存不足");
            }
        }

        // 3. 创建订单（本地事务）
        Order order = buildOrder(dto, userId, addrResult.getData());
        orderMapper.insert(order);
        // ...

        return toDTO(order);
    }
}
```

> **必须使用 `@EnableFeignClients`**：order-service 启动类必须加 `@EnableFeignClients(basePackages = "com.ecommerce.order.feign")`，否则所有 Feign 接口不会被 Spring 扫描为 Bean，调用时抛出 `NoSuchBeanDefinitionException`。
>
> ```java
> @SpringBootApplication
> @EnableDiscoveryClient
> @EnableFeignClients(basePackages = "com.ecommerce.order.feign")
> @MapperScan("com.ecommerce.order.mapper")
> public class OrderServiceApplication {
>     public static void main(String[] args) {
>         SpringApplication.run(OrderServiceApplication.class, args);
>     }
> }
> ```
>
> **文件上传**：Spring Cloud Gateway 默认限制 multipart 上传大小。若商品图片上传需经过 Gateway，应在 `application.yml` 中配置：
> ```yml
> spring:
>   cloud:
>     gateway:
>       routes:
>         - id: product-service
>           # ...
>           filters:
>             - name: StripPrefix    # 如需去掉路径前缀
>   codec:
>     max-in-memory-size: 10MB      # 上传文件大小限制
> ```
> 也可让前端直连 product-service 的 8083 端口做上传，绕过 Gateway。

**网关全局鉴权过滤器：**

```java
@Component
public class AuthFilter implements GlobalFilter, Ordered {

    private final GatewayJwtUtils gatewayJwtUtils;  // WebFlux 版 JWT 工具，不依赖 Servlet API
    private final ReactiveRedisTemplate<String, String> reactiveRedisTemplate;  // WebFlux 版 Redis，查黑名单

    // 无需鉴权的公开路径前缀（需与路由中无 AuthFilter 的路由保持一致）
    // 注意：秒杀商品列表/详情是公开的（/api/seckill/products），秒杀下单走 /api/orders 需登录
    private static final List<String> PUBLIC_PATHS = List.of(
        "/api/auth/", "/api/products/", "/api/categories/",
        "/api/banners/", "/api/seckill/", "/api/coupons/",
        "/api/announcements/", "/api/admin/auth/"
    );

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();

        // 公开路径直接放行
        if (PUBLIC_PATHS.stream().anyMatch(path::startsWith)) {
            return chain.filter(exchange);
        }

        String token = extractToken(exchange.getRequest());
        if (token == null || !gatewayJwtUtils.validateToken(token)) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }

        Long userId = gatewayJwtUtils.getUserIdFromToken(token);

        // 检查 Token 黑名单（登出后失效），防止已登出 JWT 继续使用
        String blacklistKey = "bl:" + userId + ":" + token.substring(0, 20);
        // 注：reactiveRedisTemplate 需在构造函数中注入 ReactiveRedisTemplate<String, String>
        if (Boolean.TRUE.equals(reactiveRedisTemplate.hasKey(blacklistKey).block())) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }

        // 将 userId 写入请求头，下游服务直接读取
        ServerHttpRequest request = exchange.getRequest().mutate()
            .header("X-User-Id", userId.toString())
            .build();

        return chain.filter(exchange.mutate().request(request).build());
    }

    @Override
    public int getOrder() { return -100; }

    private String extractToken(ServerHttpRequest request) {
        String auth = request.getHeaders().getFirst("Authorization");
        if (auth != null && auth.startsWith("Bearer ")) {
            return auth.substring(7);
        }
        return null;
    }
}
```

> **⚠️ Gateway 与 Servlet API 不兼容**：Spring Cloud Gateway 基于 WebFlux（`ServerWebExchange`），而当前 `common` 模块的 `JwtUtils` 基于 Servlet API（`HttpServletRequest`），两者无法直接复用。同样，`common` 的 `GlobalExceptionHandler`（基于 `@RestControllerAdvice` + Servlet API）也无法在 Gateway 中生效——Gateway 需单独使用 `ErrorWebExceptionHandler` 做全局异常处理。**解决方案**：Gateway 模块内单独编写一个轻量 `GatewayJwtUtils`，只做 JJWT 解析 + 签名验证，不依赖 `HttpServletRequest`。下游服务（user/product/order）继续使用 `common` 模块的原有 `JwtUtils` 通过拦截器校验。Gateway 只负责鉴权前置（解析 token → 写入 `X-User-Id` 请求头），角色校验由 AdminAuthFilter 完成（写入 `X-User-Role` 请求头），下游服务的 AdminInterceptor 改为读请求头而非解析 JWT。
>
> **Gateway 需要引入 Reactive Redis**：Token 黑名单检查需要查 Redis。Gateway 不能使用 Servlet 版的 `StringRedisTemplate`，必须用 WebFlux 版的 `ReactiveRedisTemplate<String, String>`。在 Gateway 的 `pom.xml` 中需添加：
> ```xml
> <dependency>
>     <groupId>org.springframework.boot</groupId>
>     <artifactId>spring-boot-starter-data-redis-reactive</artifactId>
> </dependency>
> ```
>
> **鉴权分层设计**：
> - `AuthFilter`（GlobalFilter）：解析 JWT，写入 `X-User-Id` 请求头。白名单外的路径无 token 返回 401
> - `AdminAuthFilter`（GatewayFilter）：在 AuthFilter 之后运行，检查 JWT 中 role 是否为 "admin"，通过后写入 `X-User-Role: admin` 请求头
> - 下游服务 `UserContextInterceptor`：从请求头读取 `X-User-Id` 和 `X-User-Role`，写入 ThreadLocal。AdminInterceptor 改为检查 `UserContext.getRole()` 而非解析 JWT
>
> **AdminAuthFilter 实现**：
>
> ```java
> @Component
> public class AdminAuthFilter implements GatewayFilter, Ordered {
>
>     private final GatewayJwtUtils gatewayJwtUtils;
>
>     @Override
>     public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
>         // AuthFilter 已校验过 token，此处只做角色检查
>         String token = exchange.getRequest().getHeaders().getFirst("Authorization");
>         if (token == null || !gatewayJwtUtils.validateToken(token)
>                 || !"admin".equals(gatewayJwtUtils.getRoleFromToken(token))) {
>             exchange.getResponse().setStatusCode(HttpStatus.FORBIDDEN);
>             return exchange.getResponse().setComplete();
>         }
>         // 写入 role 请求头，下游 AdminInterceptor 直接读取
>         ServerHttpRequest request = exchange.getRequest().mutate()
>             .header("X-User-Role", "admin")
>             .build();
>         return chain.filter(exchange.mutate().request(request).build());
>     }
>
>     @Override
>     public int getOrder() { return 0; }  // 在 AuthFilter (-100) 之后执行
> }
> ```
>
> **下游服务如何获取当前用户**：Gateway 把 `X-User-Id` 和 `X-User-Role` 写入请求头，下游服务通过拦截器读取：
>
> ```java
> // common 模块中扩展 UserContext（增加 role 存储）
> public class UserContext {
>     private static final ThreadLocal<Long> USER_ID = new ThreadLocal<>();
>     private static final ThreadLocal<String> USER_ROLE = new ThreadLocal<>();
>     public static void setUserId(Long userId) { USER_ID.set(userId); }
>     public static Long getUserId() { return USER_ID.get(); }
>     public static void setRole(String role) { USER_ROLE.set(role); }
>     public static String getRole() { return USER_ROLE.get(); }
>     public static void clear() { USER_ID.remove(); USER_ROLE.remove(); }
> }
> ```
>
> ```java
> // 各业务服务的拦截器（注册到 WebMvcConfigurer）
> @Component
> public class UserContextInterceptor implements HandlerInterceptor {
>     @Override
>     public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
>         String userId = request.getHeader("X-User-Id");
>         if (userId != null) {
>             UserContext.setUserId(Long.valueOf(userId));
>         }
>         String role = request.getHeader("X-User-Role");
>         if (role != null) {
>             UserContext.setRole(role);
>         }
>         return true;
>     }
>     @Override
>     public void afterCompletion(...) { UserContext.clear(); }
> }
> ```
>
> 下游服务的 `AdminInterceptor` 改为 `UserContext.getRole() != null && "admin".equals(UserContext.getRole())` 即可，不再需要解析 JWT。

### 5.6 分布式事务 (Seata AT 模式)

下单流程跨 3 个数据库，是最典型的分部署事务场景：

```java
// order-service
@Service
public class OrderServiceImpl implements OrderService {

    @GlobalTransactional  // Seata 全局事务，替代 @Transactional
    @Override
    public OrderDTO createOrder(CreateOrderDTO dto) {
        Long userId = UserContext.getUserId();

        // 1. 远程扣库存（product_db）
        for (OrderItemDTO item : dto.getItems()) {
            productFeignClient.deductStock(item.getProductId(),
                new StockDeductDTO(item.getQuantity()));
        }

        // 2. 创建订单（order_db）
        Order order = buildOrder(dto, userId);
        orderMapper.insert(order);
        for (OrderItemDTO item : dto.getItems()) {
            OrderItem orderItem = buildOrderItem(order.getId(), item);
            orderItemMapper.insert(orderItem);
        }

        // 3. 清购物车已选项（order_db）
        cartMapper.deleteSelected(userId);

        // 任一步骤抛异常 → Seata 自动回滚所有数据库
        return toDTO(order);
    }
}
```

**Seata 配置（seata-server 独立部署或 Docker）：**

```yml
# 每个服务的 seata 配置
seata:
  enabled: true
  application-id: ${spring.application.name}
  tx-service-group: ecommerce-tx-group
  service:
    vgroup-mapping:
      ecommerce-tx-group: default
    grouplist:
      default: seata-server:8091
  enable-auto-data-source-proxy: true    # Seata 自动代理数据源（生成 undo_log）
```

> Seata AT 模式对业务代码侵入最小——加一个 `@GlobalTransactional` 注解即可，不需要改写 SQL。底层通过代理数据源自动写入 undo_log 实现回滚。
>
> **Feign 调用如何加入全局事务**：Seata 的 `spring-cloud-starter-alibaba-seata` 依赖会自动注册一个 Feign 拦截器（`SeataFeignClient`），将当前全局事务的 XID 写入请求头传给下游服务。下游服务收到 XID 后自动加入同一个全局事务。也就是说——标注 `@GlobalTransactional` 的方法中所有 Feign 调用都会被自动纳入事务范围，无需手动传递 XID。
>
> **前提**：每个参与分布式事务的服务需引入 `spring-cloud-starter-alibaba-seata`，并在 `ecommerce_user`、`ecommerce_product`、`ecommerce_order` **三个业务库中各执行一次** Seata 提供的 `undo_log` 建表 SQL：
>
> ```sql
> -- 每个业务库都需执行（Seata AT 模式回滚日志表）
> CREATE TABLE IF NOT EXISTS `undo_log` (
>     `id`            BIGINT(20)   NOT NULL AUTO_INCREMENT,
>     `branch_id`     BIGINT(20)   NOT NULL,
>     `xid`           VARCHAR(100) NOT NULL,
>     `context`       VARCHAR(128) NOT NULL,
>     `rollback_info` LONGBLOB     NOT NULL,
>     `log_status`    INT(11)      NOT NULL,
>     `log_created`   DATETIME     NOT NULL,
>     `log_modified`  DATETIME     NOT NULL,
>     PRIMARY KEY (`id`),
>     UNIQUE KEY `ux_undo_log` (`xid`, `branch_id`)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
> ```
>
> 该 SQL 可从 [Seata 官方仓库](https://github.com/apache/incubator-seata) 的 `script/client/at/db/mysql.sql` 获取最新版本。

### 5.7 熔断降级 (Sentinel)

```java
// order-service 的 Feign 接口加 fallback
@FeignClient(
    name = "product-service",
    fallbackFactory = ProductFeignFallbackFactory.class

public interface ProductFeignClient {
    // ...
}

@Component
public class ProductFeignFallbackFactory implements FallbackFactory<ProductFeignClient> {
    @Override
    public ProductFeignClient create(Throwable cause) {
        return new ProductFeignClient() {
            @Override
            public Result<ProductDTO> getProduct(Long id) {

            }
        };
    }
}
```

## 六、数据库拆分

### 6.1 拆分方案

```
当前:  ecommerce (单库，20+ 张表)

拆分后:
  ecommerce_user     → user, admin, address, feedback,
                       conversation, chat_message, quick_reply,
                       announcement

  ecommerce_product  → product, product_sku, category, banner,
                       favorite, seckill_product, seckill_session,
                       search_log, hot_keyword

  ecommerce_order    → cart, `order` (含退款字段: refund_type,
                       refund_reason, refund_status 等),
                       order_item, payment_session,
                       review, review_comment, review_like,
                       coupon, user_coupon
```

> refund 不是独立表——当前实现将退款字段（`refund_type`, `refund_reason`, `refund_status`, `refund_amount` 等）直接扩展在 `order` 表上，因此拆分后仍在 order_db 中。

**⚠️ 分布式 ID 必须启用**：拆分后三个库各自自增 ID（都从 1 开始），`order_item.product_id` 跨库引用可能匹配到错误商品。需在每个服务的 `application.yml` 中配置 MyBatis-Plus 雪花算法：

```yml
mybatis-plus:
  global-config:
    db-config:
      id-type: assign_id     # 雪花算法，全局唯一 ID
```

> 存量数据迁移前先评估：若已有大量自增 ID 数据，迁移脚本中需对引用字段（如 order_item 的 product_id、cart 的 product_id）做 ID 映射替换。

### 6.2 跨库查询的处理

拆分后，原来 JOIN 查询的场景需要改为服务调用：

```java
// 原来（单体）：SQL JOIN
// SELECT o.*, p.name, p.main_image
// FROM `order` o JOIN product p ON o.product_id = p.id

// 拆分后（微服务）：两步调用
// 1. 查订单列表（order_db）
List<Order> orders = orderMapper.selectByUserId(userId);

// 2. 批量查商品信息（通过 Feign 调 product-service）
List<Long> productIds = orders.stream()
    .flatMap(o -> o.getItems().stream().map(OrderItem::getProductId))
    .distinct().toList();
Result<List<ProductDTO>> products = productFeignClient.batchGetProducts(productIds);

// 3. 内存组装
Map<Long, ProductDTO> productMap = products.getData().stream()
    .collect(Collectors.toMap(ProductDTO::getId, Function.identity()));
for (Order order : orders) {
    for (OrderItem item : order.getItems()) {
        item.setProduct(productMap.get(item.getProductId()));
    }
}
```

> 对前端返回的 JSON 结构不变，变化只在后端的数据组装方式。

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| **分布式事务一致性** | 下单时部分操作成功部分失败 | Seata AT 模式自动回滚；关键业务加幂等校验 |
| **服务调用延迟增加** | 原来进程内调用变网络调用，响应变慢 | Feign 连接池复用；Redis 缓存热点数据；Sentinel 熔断防止雪崩 |
| **跨库 JOIN 迁移遗漏** | 页面数据缺失或 N+1 查询 | 拆分前梳理所有跨表查询，改为批量 Feign 调用 + 内存组装 |
| **运维复杂度上升** | 容器从 5 个变 10+ 个 | Docker Compose 统一编排；Nacos 健康检查自动摘除故障节点 |
| **调试困难** | 单次请求跨多个服务，日志分散 | 统一日志格式加 traceId；开发环境用 docker-compose logs -f |
| **JWT 鉴权迁移** | 原来拦截器逻辑分散在各服务 | 鉴权统一上移 Gateway，下游服务只读 X-User-Id 请求头 |

---

## 十、决策建议

| 场景 | 建议 |
|------|------|
| **课程强制要求微服务** | 按本方案执行，重点展示拆分策略 + 服务通信 + 分布式事务 |
| **只是想学习微服务** | 可以只拆到阶段二（用户服务），重点理解 Nacos + Gateway + Feign 的运作方式 |
| **当前项目已够用** | 不拆。单体架构对于这个规模的电商项目完全足够——部署简单、调试方便、性能也不差 |

> 微服务的本质是用「运维复杂度」换「独立扩展能力」。在流量未达瓶颈之前，单体 + 合理的模块化包结构就是最优解。
