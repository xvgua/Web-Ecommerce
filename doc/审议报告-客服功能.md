# 客服咨询功能审议报告

> 审议日期：2026-06-04
> 审议范围：客户服务/在线咨询模块全链路
> 审议目标：对照用户需求审视当前实现的偏差与不足

---

## 一、用户需求回顾

用户对客服功能的三个核心要求：

| # | 需求 | 说明 |
|---|------|------|
| 1 | **仅商品页面可咨询** | 客服入口应仅出现在商品详情页，不应在其他页面或全局位置暴露 |
| 2 | **弹窗形式** | 咨询界面以模态弹窗（dialog）呈现，而不是固定的悬浮面板 |
| 3 | **可发送商品信息** | 用户在咨询过程中，能够将当前浏览的商品信息以消息形式发送给客服 |

---

## 二、当前实现总览

### 2.1 架构

| 层面 | 技术方案 |
|------|----------|
| 通信方式 | HTTP 短轮询（3 秒间隔），非 WebSocket |
| 会话模型 | `conversation` 表 — 按 sourceType/sourceId 关联咨询来源 |
| 消息模型 | `chat_message` 表 — senderType 区分用户(1)/客服(2) |
| 客服在线判定 | 管理员最近一次发送消息是否在 5 分钟内 |
| 已读机制 | 拉取消息时自动将对方消息标记已读 |

### 2.2 当前客服入口分布

| 入口位置 | 文件 | 触发条件 | sourceType |
|----------|------|----------|------------|
| 商品详情页 - "咨询客服"按钮 | `client/src/views/product/detail.vue:107` | 始终可见（需登录） | 1 (product) |
| 订单详情页 - "联系客服"按钮 | `client/src/views/order/detail.vue:8` | 仅 `order.status === 3`（已完成） | 2 (order) |
| 全局悬浮按钮 - ChatFloatButton | `client/src/components/business/ChatFloatButton.vue` | 始终可见 | 3 (general) |
| 底部 Footer - "联系客服"链接 | `client/src/layouts/DefaultLayout.vue:137` | 始终可见 | 3 (general) |

### 2.3 当前聊天界面形式

`ChatPanel.vue` 是一个 **固定定位（fixed）的悬浮面板**（380×520px，位于右下角），而非模态弹窗。特点：

- `position: fixed; right: 20px; bottom: 80px; z-index: 9999`
- 使用 `<Teleport to="body">` 挂载到 body
- 不覆盖背景、不阻断页面交互（非模态）
- 始终固定在屏幕上，随滚动移动

## 三、问题诊断

### 问题 1：客服入口过于分散，不符合"仅商品页面"

**严重程度：高**

当前客服聊天可在 **4 个不同位置** 触发，且其中 3 个与"商品页面咨询"场景无关：

| 入口 | 问题 | 建议 |
|------|------|------|
| 订单详情页 | 订单页面的客服应通过订单关联已有的商品会话，而不是独立入口 | **移除**，订单问题应引导到订单详情内的售后流程 |
| 全局悬浮按钮 | 在所有页面可见（首页、列表、购物车等），无商品上下文 | **移除** |
| Footer 链接 | 无商品上下文，创建的是一个 sourceType=3（通用）会话 | **移除**，footer 可保留"帮助中心"链接 |
| 商品详情页 | 唯一合理的入口 | **保留并增强** |

### 问题 2：悬浮面板而非弹窗形式

**严重程度：高**

当前 `ChatPanel.vue` 是固定定位面板，与用户要求的"弹窗形式"不符：

| 对比维度 | 当前悬浮面板 | 要求的弹窗 |
|----------|-------------|-----------|
| 定位方式 | `position: fixed` | `el-dialog` 模态 |
| 背景遮罩 | 无 | 应有半透明遮罩 |
| 页面交互 | 可同时操作页面 | 聚焦于聊天 |
| 关闭方式 | 点击 X 按钮 | 点击遮罩/X按钮均可 |
| 尺寸适配 | 固定 380×520px | 应支持响应式 |
| 移动端体验 | 遮挡内容 | 可全屏或底部弹出 |

### 问题 3：无法发送商品信息给客服

**严重程度：高**

当前实现仅在创建会话时传递 `sourceType` 和 `sourceId` 作为无数据（用于会话列表展示 sourceName），**没有将商品信息作为消息发送的能力**。

具体缺失：

1. **聊天输入区没有"发送商品"按钮** — 用户无法主动推送商品卡片
2. **没有商品卡片消息类型** — 当前 `ChatMessage.contentType` 始终为 1（纯文本），不支持结构化消息
3. **首条消息不会自动附带商品信息** — `createConversation` 时 `firstMessage` 为空字符串或用户手动输入的文字，不会附带商品链接/图片/价格等信息

期望行为：用户在商品详情页打开客服弹窗后，聊天界面应有一个"发送当前商品"的功能，将商品以卡片形式发给客服，内容包括：

- 商品图片
- 商品名称（可点击跳转）
- 商品价格
- 当前选中的规格（如有）

### 问题 4：ChatPanel 作为全局组件始终挂载

**严重程度：中**

当前 `ChatPanel` 和 `ChatFloatButton` 在 `DefaultLayout.vue` 中全局渲染：

```vue
<!-- DefaultLayout.vue:151-152 -->
<ChatFloatButton />
<ChatPanel />
```

问题：

1. **全局挂载消耗资源** — 即使不打开聊天，`ChatFloatButton` 也持续轮询客服在线状态（30s 间隔）
2. **composable 作用域混乱** — `useChat()` 在 `DefaultLayout` 和 `ChatFloatButton` / `ChatPanel` 中被多次调用，状态共享依赖 Pinia 之外的模块级单例（模块级 `ref`），这是一种脆弱的设计
3. **不符合按需加载原则** — 客服功能应在打开时才初始化，关闭时完全销毁

### 问题 5：useChat composable 使用模块级单例模式

**严重程度：中**

```ts
// useChat.ts:8-16
const isOpen = ref(false)          // ← 模块级变量，非组合式
const conversationId = ref<number | null>(null)
// ...
```

这是一个 **非标准 composable 模式**。模块级变量使得：

- 所有调用 `useChat()` 的组件共享同一份状态（这本身是预期行为）
- 但这些状态的生命周期脱离组件生命周期（`onUnmounted` 中只清理了 poll timer，不清理状态）
- 如果聊天面板被移除再重新挂载，旧状态可能干扰新状态

建议改为 Pinia store 或使用 `provide/inject`，让状态管理更显式。

### 问题 6：缺少移动端适配

**严重程度：低**

当前 `ChatPanel` 在移动端（<768px）仍然是固定 380×520px 的悬浮面板，遮挡大量屏幕空间。弹窗形式天然更友好 — 可使用 `el-dialog` 的 `fullscreen` 属性在移动端全屏展示。

## 四、改进方案

### 4.1 入口收敛

**目标：客服入口仅保留商品详情页**

需修改的文件：

| 文件 | 操作 |
|------|------|
| `client/src/layouts/DefaultLayout.vue` | 移除 `<ChatFloatButton />` 和 `<ChatPanel />` 的全局挂载；移除 Footer "联系客服"链接改为 "帮助中心" |
| `client/src/components/business/ChatFloatButton.vue` | 可删除（如无其他引用） |
| `client/src/views/order/detail.vue` | 移除 "联系客服" 按钮（或改为链接到对应商品的客服会话） |

### 4.2 面板改弹窗

**目标：将 ChatPanel 从 fixed 面板改为基于 el-dialog 的模态弹窗**

方案：

1. **新建 `ChatDialog.vue`** — 基于 `el-dialog` 封装聊天界面
   - 使用 `el-dialog` 的 `modal` + `close-on-click-modal` 属性
   - 宽度 440px，高度自适应，最大高度 600px
   - 移动端使用 `fullscreen: true`
   - 内部结构复用现有 ChatPanel 的消息列表+输入区布局

2. **修改 `useChat.ts`** — 将状态迁移到 Pinia store `stores/chat.ts`
   - 提供 `openProductChat(productInfo)` — 专门从商品页启动
   - 不再需要 `initSourceType` / `initSourceId` 模块级变量

3. **修改商品详情页** — `openProductChat()` 改为触发弹窗打开

### 4.3 商品信息发送功能

**目标：用户可在聊天中发送当前商品卡片**

方案：

1. **扩展消息类型** — 在 `ChatMessage` 接口中增加字段：
   ```ts
   interface ChatMessage {
     // ... 现有字段
     contentType: number       // 1=文本, 2=商品卡片
     extraData?: string        // JSON: { productId, productName, productImage, price, specDesc, skuId }
   }
   ```

2. **后端支持** — `POST /api/conversations/:id/messages` 接口扩展：
   - 接受 `contentType` 和 `extraData` 字段
   - `chat_message` 表增加 `content_type`（默认 1）和 `extra_data`（TEXT，可空）列
   - 数据库迁移 SQL 一条 ALTER TABLE

3. **前端新增"发送商品"按钮** — 在聊天输入区上方或输入框左侧，增加一个小图标按钮：
   ```
   [📦 发送当前商品]
   ```
   点击后发送一条 `contentType: 2` 的消息，`extraData` 包含当前商品信息

4. **商品卡片消息渲染** — 在消息气泡中，对 `contentType === 2` 的消息渲染为商品卡片：
   ```
   ┌────────────────────────────┐
   │ [商品图]  商品名称          │
   │           ¥99.00           │
   │           [查看详情 >]      │
   └────────────────────────────┘
   ```

5. **首次打开自动推送** — 在 `openProductChat` 成功后，可自动发送一条商品信息消息（或仅在输入框预填充商品信息文本）

## 五、总结

当前客服模块的基础设施（会话管理、消息轮询、管理员端面板）是扎实的，但前端用户体验层面的实现与需求存在 **三处原则性偏差**：

1. **入口泛滥** — 4 个入口 vs. 需求要求的 1 个（仅商品页）
2. **交互形式不符** — 固定悬浮面板 vs. 需求要求的弹窗
3. **缺失核心能力** — 无法向客服发送商品信息

建议按优先级顺序实施改进：
1. 先收敛入口 + 面板改弹窗（UX 层面，改动集中在 3-4 个前端文件）
2. 再增加商品信息发送功能（全栈改动，涉及数据库、后端、前端消息渲染）
3. 最后将 composable 迁移到 Pinia store（代码质量改进，不影响功能）
