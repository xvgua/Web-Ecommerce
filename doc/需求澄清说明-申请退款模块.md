# 申请退款模块 — 需求澄清说明

> 编写日期：2026-06-04
> 状态：待用户确认

## 一、背景

当前项目中，订单流程已完整覆盖"创建→支付→发货→收货"，但**退款模块仅有一个骨架**：前端按钮和后端接口虽然已通，但点击后只是简单地将订单状态改为"退款中(5)"并恢复库存，缺少完整的退款业务流程。

当前项目的退款相关现有能力：

| 已有能力                           | 状态      | 说明                                                            |
| ---------------------------------- | --------- | --------------------------------------------------------------- |
| 前端"申请退款"按钮                 | 已添加    | 订单列表页（待发货/待收货/已完成）+ 订单详情页（待发货/待收货） |
| 后端 `PUT /api/orders/{id}/refund` | 仅骨架    | 直接改状态为 REFUNDING，恢复库存，无退款原因/金额等             |
| 订单状态 `REFUNDING = 5`           | 已定义    | 前端已显示"退款中"标签（warning 颜色）                          |
| `restoreStock()` 方法              | 已有      | 取消订单时复用，退款也在用                                      |
| 管理后台订单管理                   | 基础 CRUD | 无退款审核相关功能                                              |

**核心问题**：当前"退款"只是一个状态切换，缺少以下关键环节：

- 用户**提交退款申请**的表单（退款原因、退款类型、金额、凭证）
- 管理员**审核退款**的流程（同意/拒绝）
- 退款**状态流转**（申请中→审核中→已退款/已拒绝）
- 退款**记录追溯**（独立的退款表）

## 二、需要澄清的核心问题

### Q1：退款类型

退款业务通常分两种场景，你需要支持哪些？

**方案 A — 仅退款（不退货）**

- 适用于：已付款未发货、商品已收到但有质量问题协商仅退款
- 流程：用户申请 → 管理员审核 → 退款到账
- 优点：简单，无物流逆向
- 缺点：无法处理"退货退款"场景

**方案 B — 仅退货退款**

- 适用于：已收到货、不满意需要退货
- 流程：用户申请 → 管理员审核通过 → 用户寄回商品 → 管理员确认收货 → 退款到账
- 优点：完整的电商退货流程
- 缺点：需要退货地址、退货物流跟踪

**方案 C — 两者都支持（推荐）**

- 未发货订单：仅退款
- 已收货订单：用户可选择"仅退款"或"退货退款"
- 优点：覆盖全场景
- 缺点：实现量相对较大

### Q2：退款申请表单

用户点击"申请退款"后，应该看到什么样的界面？

**方案 A — 简单弹窗（最小改动）**

- 一个对话框：选择退款原因（下拉）、填写退款说明（文本框）、输入退款金额
- 优点：实现快
- 缺点：功能有限，无法上传凭证

**方案 B — 独立退款申请页**

- 跳转到独立页面 `/orders/{id}/refund/apply`
- 包含：退款类型选择、退款商品勾选（支持部分退款）、退款原因、退款金额、图片凭证上传、退款说明
- 优点：功能完整，体验好
- 缺点：需要新建页面

**方案 C — 在订单详情页内嵌表单**

- 在订单详情页下方展开退款表单区域
- 优点：不跳转，上下文连贯
- 缺点：订单详情页会变得复杂

### Q3：退款原因

退款原因应该怎么设计？

**方案 A — 固定枚举（推荐）**

- 预设几个退款原因供用户选择：不想要了、买错了、商品与描述不符、商品破损、未按约定时间发货、其他
- 选择"其他"时可填写补充说明
- 优点：结构化，便于统计分析

**方案 B — 自由文本**

- 用户自行输入退款原因
- 优点：灵活
- 缺点：不便于分类统计

**方案 C — 枚举 + 自由说明**

- 下拉选择原因 + 补充说明文本框（选填）
- 优点：兼顾结构和灵活

> **请选择：** 退款原因用什么方式？

### Q4：退款金额

退款金额如何确定？

**方案 A — 固定全额退款**

- 退款金额 = 订单实付金额，不可修改
- 优点：简单、无争议
- 缺点：不支持部分退款

**方案 B — 用户可填金额**

- 用户自行填写期望退款金额（≤ 实付金额）
- 管理员审核时可调整
- 优点：支持部分退款、协商退款
- 缺点：可能出现金额争议

**方案 C — 按商品部分退款（推荐）**

- 用户勾选需要退款的商品，系统自动计算金额
- 适用于订单中含多件商品，只退其中一部分
- 优点：精确、公平
- 缺点：实现稍复杂

> **请选择：** 退款金额如何确定？

### Q5：管理员审核流程

退款申请提交后，管理员端如何处理？

**方案 A — 自动通过（当前行为）**

- 用户提交即生效，直接改状态 + 恢复库存
- 优点：零管理成本
- 缺点：无法拒绝不合理退款

**方案 B — 管理员手动审核（推荐）**

- 管理后台新增"退款审核"列表
- 管理员可查看退款申请详情 → 同意（退款+恢复库存）或 拒绝（填写拒绝原因）
- 优点：可控
- 缺点：需新增管理后台页面

**方案 C — 条件自动审核**

- 未发货订单：自动通过
- 已收货订单：需管理员审核
- 优点：兼顾效率和可控

> **请选择：** 退款审核流程如何设计？

### Q6：退款状态流转

退款从申请到完成应该经历哪些状态？

以下是建议的状态机：

```
用户申请 → 待审核(PENDING_REVIEW)
              ├── 管理员拒绝 → 已拒绝(REJECTED) [终态]
              └── 管理员通过 → 退款中(REFUNDING)
                                  ├── 仅退款 → 已退款(REFUNDED) [终态]
                                  └── 退货退款 → 待退货(WAITING_RETURN)
                                                    └── 用户填写退货物流 → 待收货(RETURN_SHIPPED)
                                                                              └── 管理员确认收货 → 已退款(REFUNDED) [终态]
```

### Q7：退款记录存储

退款数据如何存储？

**方案 A — 复用 Order 表扩展字段（不推荐）**

- 在 `order` 表增加 `refund_reason`、`refund_amount`、`refund_status` 等字段
- 优点：改动小
- 缺点：一个订单只能退一次，无法记录多次退款历史

**方案 B — 独立 Refund 表（推荐）**

- 新建 `refund` 表，包含：订单ID、退款金额、退款类型、退款原因、退款状态、凭证图片、拒绝原因、退货物流信息、时间线
- 一个订单可关联多条退款记录（部分退款场景）
- 优点：数据完整、可追溯
- 缺点：新增实体

### Q8：退款后库存与优惠券处理

退款成功后，库存和优惠券应该如何处理？

**库存处理：**

| 选项                              | 说明                                   |
| --------------------------------- | -------------------------------------- |
| A. 退款即恢复库存                 | 当前行为，`restoreStock()`             |
| B. 仅"退货退款"确认收货后恢复库存 | 仅退款不恢复（因为货还在用户手上）     |
| C. 根据退款类型决定               | 退货退款→确认收货后恢复；仅退款→视情况 |

**优惠券处理：**

| 选项          | 说明                         |
| ------------- | ---------------------------- |
| A. 不退优惠券 | 优惠券已消耗，退款后不返还   |
| B. 退还优惠券 | 退款后优惠券恢复可用状态     |
| C. 部分退还   | 按退款商品占比退还优惠券金额 |

## 三、建议的最小可行方案（MVP）

综合考虑实验要求和实现成本，建议以下 MVP 范围：

### 后端

1. 新增 `Refund` 实体 + `refund` 表（退款类型、原因、金额、状态、凭证、拒绝原因）
2. 改造 `OrderController.refund()` → 创建退款申请而非直接改状态
3. 新增 `RefundController`（用户端：提交申请、查看详情、撤销申请）
4. 新增 `AdminRefundController`（管理后台：退款列表、审核通过/拒绝）
5. 退款状态机：待审核 → 审核通过(退款中) → 已退款 / 已拒绝
6. 退款后库存恢复在审核通过时触发（而非申请时）

### 前端 — 客户端

1. 退款申请页 `/orders/{id}/refund/apply`（退款类型、原因、金额、说明）
2. 退款详情/进度页 `/orders/{id}/refund`（状态时间线、审核结果、退货物流）
3. 改造订单详情页和订单列表页的"申请退款"按钮逻辑（已申请时显示"查看退款进度"）

### 前端 — 管理后台

1. 退款管理页（列表、状态筛选）
2. 退款详情弹窗/页（查看申请内容、审核操作）

### 不纳入 MVP

- 退货退款（仅做"仅退款"）
- 图片凭证上传
- 部分退款（整单退）
- 退款金额调整
- 退款数据统计 Dashboard
- 优惠券退还
