## 一、现有搜索能力盘点

| 功能点     | 实现状态    | 实现方式                                             |
| ---------- | ----------- | ---------------------------------------------------- |

## 二、需要澄清的核心问题

### 2.1 精准搜索 vs 模糊搜索 — 用户如何切换？

当前项目只做"模糊匹配"（子串 LIKE、全文索引、编辑距离），没有"精准搜索"模式。

| 方案  | 描述                                      | 优势                    | 劣势                            |
| ----- | ----------------------------------------- | ----------------------- | ------------------------------- |
| **A** | 默认模糊，结果页提供"精确匹配"切换开关    | 用户主动选择，意图明确  | 需要额外 UI 元素                |
| **B** | 搜索框提供下拉选项（模糊/精确）           | 搜索前即可指定搜索模式  | 普通用户不理解"模糊/精确"的含义 |
| **C** | 搜索关键词加引号表示精确（如 `"关键词"`） | 无额外 UI，高级用户友好 | 普通用户不知道这个用法          |
| **D** | 不做精准搜索，保持现状                    | 简单，无开发成本        | 不满足需求                      |

> **待决策问题 1：精准搜索的用户触发方式选哪种？**
> 采用方案B ，搜索框提供下拉选项（模糊/精确）

### 2.2 "热门搜索词"的定义与展示位置

热门搜索词当前完全不存在，需要从零设计。

#### 数据来源

- 需新建 `search_log` 表记录每次搜索（关键词、用户ID、搜索时间）
- 热门搜索词 = 统计最近 N 天的 top K 关键词
- 是否需要过滤敏感词？（如需要，是否需要审核机制？）

#### 展示位置

| 方案  | 描述                                | 适用场景                |
| ----- | ----------------------------------- | ----------------------- |
| **A** | 搜索框获得焦点时，在下拉面板展示    | 类似百度/淘宝首页搜索框 |
| **B** | 独立"搜索发现"页面                  | 类似微博热搜榜          |
| **C** | 两者结合（焦点下拉 + 独立页面入口） | 最完整                  |

> 采用方案A ，搜索框获得焦点时，在下拉面板展示

#### 展示形式

- 纯文字列表？
- 带排名序号（1, 2, 3...）？
- 带 🔥 或 "热" 标签？
- 标签云风格（不同颜色/大小表示热度）？
- 点击直接跳转搜索结果？
  > 采用方案带 🔥 或 "热" 标签

#### 更新策略

- **实时计算**：每次搜索后重新统计（性能开销大）
- **定时计算**：每小时/每天统计一次
- **手动配置**：管理员在后台手动设置热门词
- **混合模式**：自动统计 + 管理员可置顶/干预

> **待决策问题 2：热门搜索词展示在哪里？展示形式如何？更新策略选哪种？**
> 采用方案A ，搜索框获得焦点时，在下拉面板展示，带 🔥 或 "热" 标签，定时计算

### 2.3 搜索建议 / 自动补全 — 是否要做？

当前搜索框在下拉中**仅展示历史记录**，不展示实时的商品名/关键词联想。

| 方案  | 描述                               | 触发条件                                           | 后端影响                   |
| ----- | ---------------------------------- | -------------------------------------------------- | -------------------------- |
| **A** | 实时商品名联想                     | 用户输入时请求 `/api/products/suggest?keyword=xxx` | 需新增 suggest API         |
| **B** | 仅展示历史和热门词（不做实时联想） | 搜索框获得焦点时                                   | 仅需热门词 API，开发量最小 |
| **C** | 搜索关键词联想（非商品名）         | 用户输入时根据历史搜索词做联想                     | 需 search_log 表           |

> **待决策问题 3：是否需要实时搜索建议（autocomplete/suggest）？如果需要，联想的是商品名还是搜索关键词？**
> 暂且不需要搜索建议

### 2.4 搜索范围 — 搜什么字段？

当前搜索仅匹配 `product.name`（商品名称）。

是否还需要搜索以下字段：

- [ ] 商品描述 (`product.description`)
- [ ] 商品详情 (`product.detail`，富文本内容)
- [ ] 分类名称（如搜"手机"能匹配到"智能手机"分类下的商品）
- [ ] 商品标签/规格（如果有的话）

> **待决策问题 4：搜索范围是否要从"仅商品名"扩展到其他字段？**
> 可以匹配到商品名称

## 三、推荐优先级

根据当前项目（课程作业/毕设级别电商）的定位，建议分两级实现：

### 🔴 必须实现（核心需求）

| 功能       | 建议方案                                                  |
| ---------- | --------------------------------------------------------- |
| 精准搜索   | 方案 C — 引号触发精确匹配，无额外 UI 开销                 |
| 热门搜索词 | 自动统计 + 搜索框焦点下拉展示，纯文字带热度标签，点击即搜 |
| 搜索词日志 | 新建 `search_log` 表，异步记录，不影响搜索响应速度        |

### 🟡 可选实现（锦上添花）

| 功能           | 建议方案                                                |
| -------------- | ------------------------------------------------------- |
| 实时搜索建议   | 如有余力则做（方案 A），否则仅历史+热门词即可（方案 B） |
| 扩展搜索范围   | 如有余力则扩展 `description` 字段                       |
| 后台管理热门词 | 如有余力则做                                            |
