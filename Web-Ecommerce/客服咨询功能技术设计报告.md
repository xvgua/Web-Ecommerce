## 二、技术方案选型

### 2.1 通信方式：HTTP 短轮询（推荐）

| 方案 | 优点 | 缺点 | 适用性 |
|------|------|------|--------|
| **HTTP 短轮询** | 零额外依赖，与现有架构一致；实现简单 | 有延迟（3-5秒），服务器压力略大 | ✅ 学习项目首选 |
| WebSocket | 实时性高，双向通信 | 需要 `spring-boot-starter-websocket` + 前端 `socket.io-client`，架构复杂度大增 | 可选，后续升级 |
| SSE | 服务端单向推送，比 WS 轻量 | 仅支持服务端→客户端，需客户端发请求配合 | 不推荐 |

**建议**：采用 HTTP 短轮询（3 秒间隔），理由：
- 学习项目，客服并发量极低（1-2 个客服），轮询压力可忽略
- 零额外依赖，前后端与现有架构完全一致
- 后续可平滑升级到 WebSocket（接口层不变，仅替换传输层）

### 2.2 客服在线状态判断

- 管理后台不设"在线/离线"手动切换按钮
- 约定：客服在管理后台**最近 5 分钟内有操作**视为在线
- 每次打开/操作客服管理页面时更新 `last_active_time`
- 客服关闭页面超过 5 分钟自动视为离线

## 三、数据库设计

### 3.1 `conversation` — 会话表

```sql
CREATE TABLE IF NOT EXISTS `conversation` (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id       BIGINT        NOT NULL COMMENT '用户ID',
  username      VARCHAR(50)   NOT NULL COMMENT '用户名',
  avatar        VARCHAR(500)  DEFAULT '' COMMENT '用户头像',
  subject       VARCHAR(200)  DEFAULT '' COMMENT '会话主题（自动生成：商品咨询/订单咨询/其他）',
  source_type   TINYINT       NOT NULL DEFAULT 1 COMMENT '来源: 1=商品详情 2=订单详情 3=其他',
  source_id     BIGINT        DEFAULT NULL COMMENT '关联的商品ID或订单ID',
  source_name   VARCHAR(200)  DEFAULT '' COMMENT '关联对象名称（商品名/订单号）',
  status        TINYINT       DEFAULT 1 COMMENT '1=进行中 2=已关闭',
  unread_count  INT           DEFAULT 0 COMMENT '客服未读消息数',
  user_unread   INT           DEFAULT 0 COMMENT '用户未读消息数',
  last_message  VARCHAR(500)  DEFAULT '' COMMENT '最后一条消息摘要',
  last_active   DATETIME      DEFAULT CURRENT_TIMESTAMP COMMENT '最后活动时间',
  create_time   DATETIME      DEFAULT CURRENT_TIMESTAMP,
  close_time    DATETIME      DEFAULT NULL,
  INDEX idx_user_id (user_id),
  INDEX idx_status (status),
  INDEX idx_last_active (last_active)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 3.2 `chat_message` — 消息表

```sql
CREATE TABLE IF NOT EXISTS `chat_message` (
  id              BIGINT AUTO_INCREMENT PRIMARY KEY,
  conversation_id BIGINT        NOT NULL,
  sender_type     TINYINT       NOT NULL COMMENT '1=用户 2=客服',
  sender_id       BIGINT        NOT NULL COMMENT '发送者ID',
  sender_name     VARCHAR(50)   NOT NULL,
  sender_avatar   VARCHAR(500)  DEFAULT '',
  content         TEXT          NOT NULL,
  content_type    TINYINT       DEFAULT 1 COMMENT '1=文字 2=图片',
  is_read         TINYINT       DEFAULT 0 COMMENT '0=未读 1=已读',
  create_time     DATETIME      DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_conversation_id (conversation_id),
  INDEX idx_create_time (create_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 4.2 Controller & API

#### 用户端 API（`/api/conversations`）

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| `POST` | `/api/conversations` | 用户 | 创建新会话（指定 sourceType + sourceId） |
| `GET` | `/api/conversations/current` | 用户 | 获取当前用户的所有会话列表 |
| `GET` | `/api/conversations/{id}/messages` | 用户 | 获取指定会话的消息列表（含标记已读） |
| `POST` | `/api/conversations/{id}/messages` | 用户 | 发送消息 |
| `GET` | `/api/conversations/{id}/unread` | 用户 | 获取该会话的未读消息数 |
| `PUT` | `/api/conversations/{id}/close` | 用户 | 关闭会话 |

#### 管理端 API（`/api/admin/conversations`）

| 方法 | 路径 | 鉴权 | 说明 |

### 4.4 核心 Service 逻辑

```
ConversationService:
├── createConversation(userId, sourceType, sourceId, firstMessage)
│     → 创建会话 + 首条消息
│     → 返回 conversationId
├── getMessages(conversationId, userId/isAdmin)
│     → 拉取消息列表
│     → 标记对方发送的消息为已读
│     → 更新 last_active
├── sendMessage(conversationId, senderType, senderId, content)

│     → 更新 last_active

```

## 七、关键技术要点

### 7.1 轮询策略

```ts
// useChat.ts 伪代码
let pollTimer: number | null = null

function startPolling(conversationId: number) {
  pollTimer = setInterval(async () => {
    // 1. 拉取新消息（用 lastMessageId 做增量）
    const newMessages = await getNewMessages(conversationId, lastMessageId)
    if (newMessages.length > 0) {
      messages.value.push(...newMessages)
      lastMessageId = newMessages[newMessages.length - 1].id
      scrollToBottom()
    }
    
    // 2. 更新客服在线状态
    csOnline.value = await getCsStatus()
  }, 3000) // 3 秒间隔
}
```

### 7.2 客服在线判断

```java
// CustomerServiceStatusService.java
public boolean isOnline() {
    // 查询 admin 表或 conversation 表最近一次客服操作时间
    LocalDateTime lastActive = conversationMapper
        .selectLastAdminActive();
    if (lastActive == null) return false;
    return Duration.between(lastActive, LocalDateTime.now())
        .toMinutes() < 5;
}
```

简化方案：客服打开客服管理页面时，每 3 秒轮询也算"活动"。可以在 `admin` 表加一个 `last_active` 字段，每次管理员请求客服 API 时更新。

### 7.3 消息已读机制

- 用户拉取消息时：标记所有 `sender_type=2`（客服）的消息为已读
- 客服拉取消息时：标记所有 `sender_type=1`（用户）的消息为已读
- 会话列表中：未读数 = 对方未读消息数

## 十、潜在风险与注意事项

1. **轮询对服务器压力** — 目前是学习项目，单用户场景下 3 秒轮询仅每秒 0.33 次请求，完全可以忽略。若未来扩展，可升级 WebSocket。

2. **消息存储** — 聊天消息不做物理删除，仅软关闭会话（`status=2`）。长期运行需考虑消息表归档策略，当前可忽略。

3. **用户隔离** — 用户只能看到自己的会话，客服（admin）可以看到所有会话。与现有的 `UserContext` / `AdminInterceptor` 机制一致。

4. **图片消息** — 当前设计预留了 `content_type=2`（图片），但 Phase 1 仅实现文字消息。图片消息可后续扩展。
